Log4j 2 API → log4j-to-slf4j → SLF4J 1.7.x → 实际日志框架 绑定流程解析

概览

Log4j-2 在初始化时通过 Provider 机制（ProviderUtil/Provider）发现 log4j-to-slf4j 的 provider，
这个 provider 会把 Log4j 的 LoggerContextFactory 替换成 SLF4JLoggerContextFactory，
于是 Log4j 的 Logger 请求被转成 org.slf4j.Logger 并调用 SLF4J；
SLF4J 1.7.x 在初始化时通过 StaticLoggerBinder 将 org.slf4j.Logger 绑定到具体实现（如 Logback）。

1. Log4j 启动时加载 Provider

  • LogManager 静态初始化时会调用 ProviderUtil.getProviders()。
  • ProviderUtil 通过 ServiceLoader.load(Provider.class) 扫描 META-INF/services/org.apache.logging.log4j.spi.Provider，
    同时兼容 META-INF/log4j-provider.properties。
  • 因此 log4j-to-slf4j jar 在 META-INF 下注册了对应的 provider（SLF4JProvider）。

2. Provider 返回 LoggerContextFactory

  • Provider.loadLoggerContextFactory() 返回 SLF4JLoggerContextFactory。
  • LogManager 会把它设置为全局的 LoggerContextFactory。

3. SLF4JLoggerContextFactory

  • 内部持有一个单例的 SLF4JLoggerContext。
  • 构造器会检测是否存在 SLF4J → Log4j 的反向桥接（org.slf4j.helpers.Log4jLoggerFactory），
    避免出现环路。

4. SLF4JLoggerContext

  • getLogger(name) 内部逻辑：
  • 即调用 SLF4J 的 LoggerFactory.getLogger(name)，
    再封装成 Log4j 的 ExtendedLogger。

7. 注意点

  • 避免循环桥接：Log4j → SLF4J 与 SLF4J → Log4j 不能同时存在，否则会报错。
  • 避免多绑定：classpath 上只能有一个 StaticLoggerBinder，否则 SLF4J 会报警告。
